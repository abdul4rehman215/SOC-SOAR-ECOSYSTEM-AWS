====================================================================
WAZUH ARCHITECTURE NOTES
PROJECT 03 — WAZUH ALL-IN-ONE DEPLOYMENT ON AWS EC2
====================================================================

1. PURPOSE OF THIS DEPLOYMENT
--------------------------------------------------------------------
This project deploys Wazuh as the core SIEM/XDR layer of the SOC-SOAR
ecosystem. The goal is to provide:

- centralized log analysis and alerting
- endpoint monitoring via Wazuh agents
- vulnerability detection visibility
- compliance checks (SCA / CIS posture)
- file integrity monitoring (FIM)
- baseline SOC dashboards and investigation workflows

This deployment is used as the foundation for later projects involving:
- TheHive case management integration
- Cortex analyzers/responder automation
- MISP threat intel enrichment
- Suricata / Zeek network visibility integration
- VirusTotal enrichment and active response
- AWS CloudTrail ingestion and monitoring


2. DEPLOYMENT MODEL USED (ALL-IN-ONE)
--------------------------------------------------------------------
All-in-one means these components run on ONE EC2 host:

- Wazuh Manager
- Wazuh Indexer
- Wazuh Dashboard
- Filebeat (Wazuh → Indexer forwarding)

Benefits:
- fastest deployment path for lab environments
- simpler troubleshooting
- fewer moving parts for initial SOC build

Tradeoffs:
- heavier memory/storage requirements
- less realistic than a distributed production deployment
- indexer and dashboard share the same host resources


3. EC2 SIZING STRATEGY (WHAT WORKED RELIABLY)
--------------------------------------------------------------------
Recommended EC2 sizing for stable all-in-one operation:

- Instance Type: t2.large / t3.large
- vCPU: 2
- RAM: 8 GB minimum (recommended for stability)
- Storage: 100 GB+ (gp3 recommended)

Reason:
- Indexing and dashboard queries are memory and IO intensive
- Low memory causes:
  - high swap usage
  - indexer instability/crash
  - slow or unstable dashboard behavior


4. CORE COMPONENT ROLES
--------------------------------------------------------------------
Wazuh Agent (Endpoints):
- installed on monitored systems (Windows/Linux/macOS)
- collects security telemetry:
  - auth logs, event logs
  - FIM events
  - inventory data
  - SCA results
  - custom logs and integrations
- communicates securely with manager

Wazuh Manager (Server):
- central analysis and rule engine
- decoders + rules apply detection logic
- generates alerts and archives events
- manages agent configuration and enrollment

Wazuh Indexer:
- stores and indexes security events and alerts
- enables fast search and correlation
- supports dashboard queries and visualizations

Wazuh Dashboard:
- web UI for management and monitoring
- dashboards for:
  - threat events
  - vulnerabilities
  - compliance
  - FIM changes
  - agent health and inventory
- interacts with manager API and indexer


5. COMPONENT COMMUNICATION & PORTS
--------------------------------------------------------------------
Default communication ports:

A) Agent → Wazuh Manager
- 1514/TCP (default): agent event communication
- 1514/UDP (optional): disabled by default

B) Agent Enrollment (Registration)
- 1515/TCP: agent enrollment via automatic request

C) Wazuh Manager API
- 55000/TCP: RESTful API used by dashboard and external integrations

D) Wazuh Manager → Wazuh Indexer
- Filebeat ships alerts/events to indexer using TLS
- Indexer default port: 9200/TCP

E) Indexer cluster communication (cluster only)
- 9300–9400/TCP (used if indexer nodes are clustered)

F) Wazuh Dashboard
- 443/TCP: HTTPS Web UI access

Other optional ports:
- 514/UDP (Syslog collector): disabled by default
- 1516/TCP (cluster daemon): used only in manager clustering


6. SECURITY GROUP MODEL (AWS)
--------------------------------------------------------------------
Principles:
- least privilege inbound access
- restrict dashboard access to admin IP / VPN
- restrict agent ports to trusted networks only
- avoid exposing indexer port publicly

Recommended inbound rules:

- 22/TCP (SSH)     → admin IP only
- 443/TCP          → admin IP or VPN only
- 1514/TCP         → agent networks/subnets only
- 1515/TCP         → agent networks/subnets only
- 55000/TCP        → admin IP/VPN only (if remote API needed)
- 9200/TCP         → internal only (avoid public exposure)

Outbound:
- allow all outbound for:
  - OS updates
  - threat intel feeds
  - API integrations
  - package downloads and repository access


7. DATA FLOW (SOC VIEW)
--------------------------------------------------------------------
High-level flow:

(Endpoints with agents)
    |
    | 1514/TCP secure event channel
    v
Wazuh Manager (decoders + rules + analysis engine)
    |
    | Alerts / archives forwarded via Filebeat (TLS)
    v
Wazuh Indexer (storage + search)
    |
    | queries
    v
Wazuh Dashboard (visualization + investigations + management)
    |
    | management/status calls
    v
Wazuh Manager API (55000/TCP)


8. CONFIGURATION BASELINE APPLIED (SOC STABLE ossec.conf)
--------------------------------------------------------------------
File:
- /var/ossec/etc/ossec.conf

This baseline enables and stabilizes:
- JSON output logging (jsonout_output, logall_json)
- alert level tuning (log_alert_level)
- secure agent connection (remote connection secure)
- rootcheck enabled with Docker/container ignores
- syscollector enabled (inventory)
- SCA enabled (compliance scanning)
- vulnerability detection enabled (Canonical/Debian/MSU/NVD feeds)
- FIM enabled (syscheck)
- key ruleset lists prepared for:
  - AWS event names (future CloudTrail ingestion)
  - suspicious programs / audit keys
  - IOC list placeholders (hashes, IPs, domains)
- authd enrollment service enabled (1515)

Operational rule:
- Always backup ossec.conf before edits
- Restart only wazuh-manager after config changes


9. VALIDATION STRATEGY
--------------------------------------------------------------------
Validation steps used:

Service validation:
- systemctl status wazuh-manager
- systemctl status filebeat
- (optional) wazuh-dashboard / wazuh-indexer service status

Log validation:
- tail -n 50 /var/ossec/logs/ossec.log

Port validation:
- ss -tuln (check 443, 1514, 1515, 55000, 9200)

Dashboard validation:
- login works
- agents panel accessible
- security events view loads
- vulnerability module visible
- FIM alerts visible (depending on activity)


10. MOST COMMON DEPLOYMENT FAILURES
--------------------------------------------------------------------
1) Dashboard down
   - 443/TCP blocked in AWS Security Group
   - dashboard service not running

2) Indexer instability/crash
   - insufficient RAM (< 8GB)
   - disk pressure or heavy swap usage

3) Agents not connecting
   - 1514/TCP blocked
   - incorrect manager IP/hostname on agent side

4) Enrollment failing
   - 1515/TCP blocked
   - auth section misconfigured or manager not restarted

5) API-related issues
   - 55000 blocked or API not responding
   - dashboard cannot retrieve status/config
