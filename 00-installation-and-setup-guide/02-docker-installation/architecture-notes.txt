====================================================================
DOCKER INSTALLATION ARCHITECTURE NOTES
PROJECT 02 — STANDARD DOCKER BASELINE (UBUNTU / AWS EC2)
====================================================================

1. PURPOSE OF THIS INSTALLATION BASELINE
--------------------------------------------------------------------
Docker is used as a standardized deployment layer for multiple SOC/SOAR
components in this portfolio. Installing Docker correctly once ensures
that future deployments (TheHive, Cortex, n8n, etc.) are:

- repeatable
- isolated from OS dependency conflicts
- easy to rebuild or redeploy
- consistent across cloud and local environments

This guide uses Docker’s official APT repository method rather than
Ubuntu’s default packages to ensure better compatibility and freshness.


2. WHY OFFICIAL DOCKER REPO (NOT DEFAULT UBUNTU PACKAGES)
--------------------------------------------------------------------
Official Docker repository provides:

- up-to-date Docker Engine (docker-ce)
- docker-compose-plugin (modern compose)
- docker-buildx-plugin
- containerd maintained with Docker ecosystem

Using default Ubuntu packages can result in:
- outdated versions
- missing compose plugin compatibility
- inconsistent behavior across machines


3. INSTALLATION TRUST MODEL (GPG + APT KEYRINGS)
--------------------------------------------------------------------
Docker repository packages are signed. Ubuntu APT verifies trust using:

- Docker GPG key stored at:
  /etc/apt/keyrings/docker.gpg

- Docker repository entry stored at:
  /etc/apt/sources.list.d/docker.list

Repository line includes:
- signed-by=/etc/apt/keyrings/docker.gpg
This enforces that only packages signed with Docker’s key are trusted.

Critical requirements:
- docker.gpg must exist
- docker.gpg must be readable by APT:
  chmod a+r /etc/apt/keyrings/docker.gpg

If this fails, APT errors occur:
- NO_PUBKEY
- repository is not signed
- signature verification failed


4. REPOSITORY SELECTION LOGIC
--------------------------------------------------------------------
Repository configuration uses system detection to ensure correctness:

- Architecture:
  dpkg --print-architecture
  Examples: amd64, arm64

- Ubuntu Codename:
  lsb_release -cs
  Examples: jammy (22.04), noble (24.04)

Repository points to:
https://download.docker.com/linux/ubuntu <codename> stable


5. SERVICE ARCHITECTURE (DOCKER DAEMON)
--------------------------------------------------------------------
Docker components installed:

- docker-ce       (Docker Engine)
- docker-ce-cli   (CLI client)
- containerd.io   (runtime)
- docker-buildx-plugin
- docker-compose-plugin

Service:
- docker.service

Expected behavior:
- Docker daemon starts at boot:
  systemctl enable docker
- Docker daemon must be running before containers work:
  systemctl start docker


6. PERMISSION MODEL (DOCKER SOCKET + GROUP)
--------------------------------------------------------------------
Docker uses a Unix socket:
- /var/run/docker.sock

By default, this socket is owned by:
- root:docker

Users must be in "docker" group to run Docker without sudo:
- usermod -aG docker $USER

Session refresh required:
- newgrp docker
or logout/login

Common permission failure:
- "permission denied while trying to connect to the Docker daemon socket"


7. NETWORK DEPENDENCIES (WHY INTERNET + DNS MATTER)
--------------------------------------------------------------------
Docker installation and usage requires:

- Internet access (apt repo, packages)
- DNS resolution (download domains, registry domains)
- HTTPS connectivity (TLS handshake)

During installation:
- curl downloads GPG key via HTTPS
- apt updates repo metadata via HTTPS

During runtime:
- docker pull uses Docker registry endpoints:
  registry-1.docker.io

If DNS fails:
- apt update fails
- curl fails
- docker pull fails
- docker run hello-world fails


8. VALIDATION REQUIREMENTS (END-TO-END TEST)
--------------------------------------------------------------------
Validation is done with:

docker run hello-world

This verifies:
- docker daemon is running
- docker can pull images from registry
- container runtime works
- local system supports container execution

Expected output includes:
"Hello from Docker!"


9. COMMON ARCHITECTURE / INSTALLATION FAILURES
--------------------------------------------------------------------
1) NO_PUBKEY error
   - GPG key missing or unreadable
   - signed-by path incorrect
   - permissions incorrect on docker.gpg

2) repository not signed
   - repo file malformed
   - GPG key not properly imported

3) Cannot connect to Docker daemon
   - docker service not running
   - docker socket not available
   - permissions issue

4) permission denied on docker.sock
   - user not in docker group
   - session not refreshed

5) hello-world fails to pull image
   - DNS issue
   - outbound blocked
   - AWS networking misconfigured


10. SECURITY NOTES (BASIC AWARENESS)
--------------------------------------------------------------------
- Docker group membership is equivalent to root-level access.
  Anyone in docker group can potentially escalate privileges.

In portfolio/lab environments:
- Acceptable tradeoff for usability
- Still recommended:
  - restrict SSH inbound access
  - apply least-privilege security groups
  - avoid exposing Docker API remotely


11. FINAL STATUS (PROJECT 02 OUTCOME)
--------------------------------------------------------------------
- Docker installed via official APT repository
- GPG key stored in /etc/apt/keyrings/docker.gpg
- Docker repo configured in /etc/apt/sources.list.d/docker.list
- Docker service enabled and running
- docker compose plugin installed and verified
- User added to docker group
- Validation completed via:
  docker run hello-world
