SOC MITRE ATT&CK Coverage Dashboard
Architecture and Data Flow

============================================================
1. PROJECT PURPOSE
============================================================

This project focuses on the ATT&CK-visibility layer of the SOC.

Its purpose is to transform MITRE-mapped Wazuh alerts into a practical
dashboard that helps SOC analysts understand:

- which ATT&CK tactics are active
- which techniques appear most often
- which ATT&CK IDs are being detected
- how attack behavior evolves over time

This project does not cover Wazuh deployment or Wazuh agent installation.
Those setup components are documented separately in other repository
folders. This project assumes Wazuh alert data with MITRE mapping is
already available.

3. ENVIRONMENT MODEL
============================================================

Attack Source
  - Kali Linux or other simulated attacker system
  - generates realistic security activity such as:
      * invalid logins
      * brute-force attempts
      * account manipulation
      * privilege-related activity

Monitored Endpoint
  - Ubuntu and/or Windows endpoint
  - already sending telemetry to Wazuh
  - produces alerts with MITRE ATT&CK field mappings

Wazuh Stack
  - Wazuh Manager
  - Wazuh Indexer
  - Wazuh Dashboard

Dashboard Layer
  - uses Wazuh alert data from wazuh-alerts-*
  - visualizes ATT&CK tactics, techniques, IDs, and timelines

============================================================
4. PRIMARY DATA SOURCE
============================================================

Main index used:
  wazuh-alerts-*

Important fields used in this project:
  - timestamp
  - rule.level
  - rule.description
  - rule.mitre.tactic
  - rule.mitre.technique
  - rule.mitre.id
  - agent.name
  - agent.ip

These fields make it possible to convert raw detections into a
structured ATT&CK-based monitoring dashboard.

============================================================
5. MITRE MAPPING LOGIC
============================================================

Wazuh alerts may contain built-in or rule-based MITRE metadata.

Examples of mapped fields:
  - rule.mitre.tactic
  - rule.mitre.technique
  - rule.mitre.id

Example ATT&CK mapping:
  Tactic: Initial Access
  Technique: Brute Force
  Technique ID: T1110

This metadata is the core of the dashboard because it allows analysts
to understand attacker behavior in a standardized way.

============================================================
6. DASHBOARD COMPONENTS
============================================================

The dashboard is built from four main visualizations:

1. MITRE - Tactics Distribution
2. MITRE - Top Techniques
3. MITRE - Technique IDs
4. MITRE - Technique Timeline

Together, these panels provide a practical ATT&CK-oriented SOC view.

============================================================
7. VISUALIZATION-BY-VISUALIZATION ROLE
============================================================

A. MITRE - Tactics Distribution
----------------------------------------
Purpose:
  Show which ATT&CK tactics are most active.

Helps answer:
  - Is the activity related to Initial Access?
  - Are Credential Access alerts increasing?
  - Is Persistence or Command and Control present?
  - Which attack lifecycle stages are most visible?

Main field:
  rule.mitre.tactic

B. MITRE - Top Techniques
----------------------------------------
Purpose:
  Show the most frequently observed ATT&CK techniques.

Helps answer:
  - Which attacker methods appear most often?
  - Is Brute Force the dominant pattern?
  - Are Valid Accounts or Account Manipulation present?
  - What technique patterns deserve attention?

Main field:
  rule.mitre.technique

C. MITRE - Technique IDs
----------------------------------------
Purpose:
  Show ATT&CK technique IDs in standardized format.

Helps answer:
  - Which Txxxx IDs are being detected?
  - How can detections be referenced consistently in reports?
  - Which ATT&CK IDs dominate the environment?

Main field:
  rule.mitre.id

D. MITRE - Technique Timeline
----------------------------------------
Purpose:
  Show how ATT&CK techniques appear over time.

Helps answer:
  - When do technique spikes occur?
  - Is there repeated brute-force activity?
  - Is attack behavior evolving across time?
  - Are multiple techniques appearing in sequence?

Main fields:
  timestamp
  rule.mitre.technique

============================================================
8. FILTERING LOGIC
============================================================

This dashboard focuses on medium to high-severity alerts to improve
SOC relevance and reduce background noise.

Primary severity filter:
  rule.level between 8 and 15

Why this matters:
  - removes lower-priority informational alerts
  - emphasizes more meaningful attack activity
  - makes the dashboard more triage-focused
  - improves analyst signal quality

This filter helps align the dashboard with realistic SOC workflows.
