SOC Compliance & CIS Benchmark Dashboard
Architecture and Data Flow

============================================================
1. PROJECT PURPOSE
============================================================

This project focuses on the compliance-visibility and security-posture
layer of the SOC.

Its purpose is to transform Wazuh SCA findings into a practical
dashboard that helps SOC analysts, security engineers, and defenders
understand:

- overall compliance posture
- pass vs fail distribution
- most frequently failing CIS controls
- posture trends over time
- where remediation should be prioritized first

This project does not cover Wazuh deployment or Wazuh agent setup.
Those components are documented separately in other repository folders.
This project assumes Wazuh SCA data is already available.

Primary filter used:
  rule.groups is sca

Important fields used in this project:
  - rule.groups
  - data.sca.check.title
  - data.sca.check.result
  - data.sca.policy
  - timestamp
  - agent.name
  - agent.id

These fields make it possible to build a compliance-focused dashboard
using SCA findings rather than general security alerts.

============================================================
5. WHAT WAZUH SCA DOES
============================================================

Wazuh SCA evaluates system configuration against security policies
and benchmark guidance.

Examples of supported policy use cases include:
  - CIS benchmarks
  - PCI-related checks
  - NIST-aligned controls
  - custom security policies

For this project, the focus is on CIS benchmark visibility.

Each evaluated check may produce results such as:
  - passed
  - failed
  - not applicable

Example check concepts:
  - Ensure ssh PermitRootLogin is disabled
  - Ensure ssh PermitEmptyPasswords is disabled
  - Ensure ssh HostbasedAuthentication is disabled
  - Ensure logging controls are configured
  - Ensure strong remote access settings are enforced

6. DASHBOARD COMPONENTS
============================================================

The dashboard is built from four main visualizations:

1. Compliance - Overall Score
2. Compliance - Pass vs Fail
3. Compliance - Top Failed CIS Checks
4. Compliance - Findings Timeline

Together, these panels provide a practical posture-monitoring view
for compliance and hardening visibility.

============================================================
7. VISUALIZATION-BY-VISUALIZATION ROLE
============================================================

A. Compliance - Overall Score
----------------------------------------
Purpose:
  Provide a high-level view of compliance posture.

Helps answer:
  - How healthy is the baseline posture overall?
  - Does the environment appear broadly aligned or weak?
  - Is the compliance posture trending toward concern?

Main concept:
  gauge-style high-level compliance indicator

Primary source logic:
  count-based SCA-derived posture visibility

B. Compliance - Pass vs Fail
----------------------------------------
Purpose:
  Show the distribution of SCA result states.

Helps answer:
  - How many checks passed?
  - How many checks failed?
  - How many checks are not applicable?

Main field:
  data.sca.check.result

Common result values:
  - passed
  - failed
  - not applicable

C. Compliance - Top Failed CIS Checks
----------------------------------------
Purpose:
  Identify the most frequently failing controls.

Helps answer:
  - Which hardening controls fail most often?
  - What should the team fix first?
  - Are the same checks failing across multiple policies?

Main fields:
  data.sca.check.title
  data.sca.policy

Additional result filter:
  data.sca.check.result = failed

D. Compliance - Findings Timeline
----------------------------------------
Purpose:
  Show how compliance findings change over time.

Helps answer:
  - Are failed findings increasing?
  - Is remediation improving the environment?
  - Are posture issues recurring over time?
  - Do pass/fail results shift after hardening work?

Main fields:
  timestamp
  data.sca.check.result

============================================================
8. FILTERING LOGIC
============================================================

This dashboard is intentionally isolated to SCA events only.

Primary filter:
  rule.groups is sca

Why this matters:
  - excludes unrelated alert types
  - prevents authentication, FIM, network, and attack alerts
    from polluting the dashboard
  - keeps the dashboard focused on configuration posture
  - improves compliance visibility quality

Additional panel-specific logic may include:
  data.sca.check.result is failed

This is especially important for the
"Compliance - Top Failed CIS Checks" panel.

============================================================
12. COMPLIANCE INTERPRETATION MODEL
============================================================

This dashboard helps teams interpret posture through several layers:

Layer 1: High-Level Status
  - Is compliance broadly healthy or weak?

Layer 2: Result Distribution
  - Are most checks passing or failing?

Layer 3: Failure Prioritization
  - Which specific controls are failing most often?

Layer 4: Time-Based Change
  - Are conditions improving, stable, or worsening?

This layered visibility makes the dashboard useful for both
operational teams and reporting stakeholders.

============================================================
13. EXAMPLE COMPLIANCE FINDINGS CONTEXT
============================================================

Typical failing CIS checks may involve:
  - insecure SSH settings
  - empty password acceptance
  - host-based authentication enabled
  - weak logging configuration
  - unsafe remote access parameters
  - incomplete hardening controls

Example policy names:
  - CIS Ubuntu Linux 24.04
  - CIS Microsoft Windows

These policy names may appear in split-series views to help identify
whether certain hardening failures are concentrated in a specific OS
or policy group.
